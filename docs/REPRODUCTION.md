# 再現計画と決定記録(プロジェクトリーダー: コンパス)

> **🚧 作成中。** 判断の根拠は元の論文 [arXiv:2608.27454](https://arxiv.org/abs/2608.27454) です。論文の本文・付録の
> どこから読み取ったかを、各決定に添えています。論文に書かれていないことは「不明」と明記し、推測で埋めていません。

## 1. 目的

論文の方法(スキルと wiki を一緒に育てる)が、**同じ手順で動き、同じ傾向の結果を出す**ことを確かめる。
最終的な採点と外部 AI との比較は別チームが行う([`HANDOFF.md`](HANDOFF.md))。

## 2. 論文が求める実験条件(再現の要件)

| ベンチマーク | 対話 | 課題数 train / val / test | 環境ツール | 推論プロンプト |
|---|---|---|---|---|
| LiveMathematicianBench | 単発 | 35 / 18 / 124 | なし(直接推論) | [`livemath.txt`](../benchmarks/prompts/livemath.txt) |
| SealQA(2026年7月版) | 多段 | 16 / 10 / 85 | `web_search`(Google Search API)、`read_file` | [`sealqa.txt`](../benchmarks/prompts/sealqa.txt) |
| SpreadsheetBench | 多段 | 80 / 40 / 280 | `bash`(Python 実行) | [`spreadsheetbench.txt`](../benchmarks/prompts/spreadsheetbench.txt) |
| OfficeQA | 多段 | 50 / 24 / 172 | `glob`、`grep`、`read` | [`officeqa.txt`](../benchmarks/prompts/officeqa.txt) |
| ALFWorld | 多段(シミュレータ) | 39 / 18 / 134 | 許可される行動の集合 | [`alfworld.txt`](../benchmarks/prompts/alfworld.txt) |

出典: 付録B・表6、付録E.1。分割とツールは先行研究(Yang et al. 2026 = SkillOpt、Alzubi et al. 2026 = EvoSkill)と
**厳密に一致させた**と書かれています。

論文のその他の条件:
- スコアは **完全な進化パイプラインを3回独立に回した平均**。検証セットが小さくゲート判定が揺れるため(付録B)。
- 有意差は、テスト分割に対する **対応ありブートストラップ(1,000回)**、p < 0.05(付録C)。
- モデルは Qwen-3.5-4B/9B、Qwen-3.6-27B、Gemma-4-31B(vLLM)と Gemini-3.5-Flash。
- 反復回数 K の値は **不明**(アルゴリズム1は記号 `K` のみ。表5が反復0〜7を区分しているが、8回と断定する根拠ではない)。反復番号の付け方も論文内で不統一(アルゴリズムは k=1..K、事例分析と図は Iteration 0 から)。温度・top-p・最大トークン・シード・ReAct の最大ステップ数・`{skill_section}` の書式も不明(ReAct は実測で約10〜20ステップ、付録D.2)。
- 公式コードは公開されていない。

## 3. 決定記録

| # | 決定 | 論文上の根拠 |
|---|---|---|
| D1 | 再現の目標は **相対的な効果**(スキルあり vs なし、wiki あり vs なし、モデル間の移植)。論文の絶対値との一致は目標にしない。 | 使うモデルが異なる(D6)。K・温度が不明。コード非公開。 |
| D2 | 課題と分割は **先行研究のものを使う**。自前で作ったり推測したりしない。入手できるまで、再現本番は始めない。 | 付録B「分割とツールは先行研究と厳密に一致」 |
| D3 | 再現本番は **3回独立実行 + 対応ありブートストラップ**、**K = 8**(反復0〜7に相当)。K は論文の指定ではなく**私の推定**。 | 付録B(3回の平均)、付録C(検定)、表5(反復0〜7) |
| D4 | 着手の順序は **LiveMath → OfficeQA → SpreadsheetBench → SealQA**。**ALFWorld は v1 の対象外**。 | 環境が軽い順。ALFWorld はステップごとに環境と対話する必要があり(E.1のプロンプトは1手ごとの形式)、`claude -p` の単発呼び出しでは足りない。 |
| D5 | 比較手法 3つ(Trace2Skill/EvoSkill/SkillOpt)は **v1 の対象外**。代わりに、論文の中心的な主張である **wiki のアブレーション**(表3・5.1節)を再現する。論文の構成は「提案役が wiki を使えない」+「Wiki Maintainer も外す」で、平均 63.7% → 48.7%。**この数値は Gemini-3.5-Flash の4ベンチマーク(ALFWorld を含まない)の平均**。 | 付録D.1は概要のみで、細部と公式コードがない。推定で作ると不公平な比較になる。 |
| D6 | v1 のモデルは **Claude**(`claude` CLI)。小型オープンモデル(vLLM)は、接続口はあるが後続フェーズ。 | 論文のモデルは入手・計算資源の確認が別途必要。OpenAI 互換の接続口は実機未検証。 |
| D7 | 最終採点は別チーム。**テストはゲートに使わず、進化の完了後に1回だけ**測る。成果物の形式は固定(`schema_version: 1`)。 | 付録C(テスト分割での検定) |
| D8 | 推論エージェントは **wiki を読めない**。 | 5.1節: 訓練ロールアウト中に wiki を読ませると平均 63.7% → 60.9% に下がる(検証・テストでは、スキルをシステムプロンプトに入れるだけ)。 |
| D9 | ゲートは **厳密な改善のみ採用**、wiki は巻き戻さない、1反復1スキルの原子的な提案。 | 3.2節、アルゴリズム1(実装済み) |
| D10 | **本番実行の前に必ずパイロット**(1回・2反復・テストなし)を回し、呼び出し数と所要時間を実測してから承認を取る。 | 下の見積もりは上限であり、ツールを使う課題は1回の呼び出しの中で複数ターンを使う。 |

## 4. 呼び出し数の見積もり(上限)

1回の実行の呼び出し数 ≈ `V + K × (T + 2 + V) + 2 × N_test`
(`V` = 検証課題数、`T` = 訓練課題数、`2` = wiki 保守と提案、`N_test` = テスト課題数、`K` = 8)。
検証がスコア 1.0 に達すると早期終了するので、実際はこれ以下です。

| ベンチマーク | 1反復あたり | 1回の実行 | **3回の実行** | パイロット(1回・2反復・テストなし) |
|---|---|---|---|---|
| LiveMath | 55 | 706 | **2,118** | 128 |
| SealQA | 28 | 404 | **1,212** | 66 |
| SpreadsheetBench | 122 | 1,576 | **4,728** | 284 |
| OfficeQA | 76 | 976 | **2,928** | 176 |
| ALFWorld(対象外) | 59 | 758 | 2,274(エピソード数。1エピソードは多数のステップ) | 136 |

- 「呼び出し」は `claude -p` の1回の起動です。ツールを使う課題は、1回の中で複数ターンを消費します。費用(金額・トークン)は
  **パイロットで実測する**までは見積もれません。
- 減らす手段: `--train-sample`(訓練課題の数を制限)、`--iters`、早期終了。ただし論文の条件からは外れます。

## 6. ベンチマークごとに必要な作業

| ベンチマーク | 課題ファイルの作り方 | 必要な追加作業 |
|---|---|---|
| **LiveMath** | `input` = 問題と選択肢、`expected` = 選択肢のラベル。`--scorer exact` | なし(データさえあれば開始できる) |
| **OfficeQA** | `input` = 質問と参照ページ、`workspace` = 財務省月報のテキスト。ツール `Read,Grep,Glob` | データの入手、答えの数値比較の採点器(許容誤差の規則は論文に記載なし) |
| **SpreadsheetBench** | `workspace` = 入力のスプレッドシート、`input` に `{workspace}` のパスを含める。ツール `Bash(python3 *)`,`Read` | データの入手、**出力ファイルとの比較を行う採点コマンド**(`$WIKISKILL_WORKSPACE` から読む)。**注意**: workspace に依存する採点は `rescore` では再実行できないため、引き渡し時は実行時の判定を `correct` として使う |
| **SealQA** | `input` = 質問。ツール `mcp__<名前>__web_search` など | **検索ツールのアダプタ**(論文は Google Search API。Claude の組み込み検索とは別物なので、差が出る)。2026年7月版のデータ |
| **ALFWorld** | — | **対象外(D4)**。環境ループ(1手ごとの観測・許可行動・履歴の差し込み)が必要 |

## 7. 開始条件(Go / No-Go)

再現本番(§3 の D3 の条件での実行)を始めてよい条件:

- [x] 進化ループ・複数回実行・引き渡し形式が実機で動く
- [x] 環境を差し込む手段(プロンプト・workspace・MCP)が実機で動く
- [ ] コミット済みの状態から作った基準 run が `check` を通る(`git_dirty: false`)
- [ ] **データと分割の入手(D2)**: 少なくとも LiveMath
- [ ] **予算の承認**: パイロットの実測値に基づく

## 8. 実行例(LiveMath、データ入手後)

```sh
# tasks.jsonl: {"id","input","expected","split"} を train/val/test の件数(35/18/124)で用意
node dist/src/cli.js evolve --tasks livemath/tasks.jsonl --out runs/livemath-pilot \
  --agent-prompt benchmarks/prompts/livemath.txt --task-desc "multiple-choice math problems" \
  --model <モデル> --iters 2 --runs 1                      # まずパイロット(テスト分割は外しておく)

node dist/src/cli.js evolve --tasks livemath/tasks.jsonl --out runs/livemath \
  --agent-prompt benchmarks/prompts/livemath.txt --task-desc "multiple-choice math problems" \
  --model <モデル> --iters 8 --runs 3                      # 本番(論文の条件)

node dist/src/cli.js check --run runs/livemath             # 引き渡し前の検査
```

アブレーション(wiki のない提案役): 同じ分割で `--proposer-no-wiki` を付けて、別のディレクトリに出力する。

## 9. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| データ・分割が入手できない/先行研究と一致しない | 再現の主張ができない | D2: 推測で作らない。入手できなければ、結果は「手法の動作確認」として報告し、再現とは呼ばない |
| 費用・時間が想定を超える | 本番が完走しない | D10: パイロットで実測してから承認 |
| 検証が小さくゲートが不安定 | 結果が run ごとに大きく揺れる | D3: 3回実行の平均と検定(論文と同じ対処) |
| Claude とオープンモデルで効果が違う | 論文の「小型モデルほど効果大」を検証できない | D6: v1 では主張しない。vLLM 経路を後続で |
| 採点器の差で結果が変わる | 外部チームの比較とずれる | 実行時の判定と生出力の両方を保存(`HANDOFF.md`)。`rescore` で再採点 |
| 論文プロンプトの転記ミス | 再現度の低下 | 解消済み: LaTeX ソースから逐語で取り込み、照合した(§5)。ただし `{skill_section}` の書式は論文に記述がなく、本ツールの選択 |
| 環境ツールが論文と別物(検索、ツール名) | 絶対値が合わない | D1: 相対効果を見る。差異を報告に明記 |
